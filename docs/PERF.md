# BidPilot 性能实测（200 页 / 26 章）

验收尺子里有一条「200 页招标文件 ≤ 20 分钟」。这份文档记录**实测数字、命令与口径**，
避免把"含 LLM 生成"和"不含 LLM"的两种耗时混在一起比较，也避免用"章节数被去重的拼接件"
冒充规模测试。

## 1. 结论

| 口径 | 实测 | 验收尺子 | 说明 |
|---|---|---|---|
| **解析 + 切章**（`load_tender`，PDF 200 页 / 5 章 / 1251 段） | **12.1 s**（3 次最好） / 12.1–25.1 s（区间） | — | pypdf 抽文 + 分页分段 + 章节切分 + 废标扫描 |
| 同上，**26 章 / 199 页 / 2943 段**（长语料） | **0.12 s** | — | 不走 pypdf；口径差异见 §2 |
| 抽取 JSON 读取 + 能力矩阵 + 计划 + 导出（`generate=False`） | 0.1–0.4 s | — | 复用已落盘的抽取结果，**0 次 LLM 调用** |
| **单次完整跑（不含 LLM 生成，PDF 口径）** | **12.5 s**（最好） / 25.5 s（最差） | 1200 s | 占预算 **1.04%** |
| 生成阶段（LLM） | **未计入** | — | 本次用 `--no-generate` 跳过；见 §5 口径 |

参考基线（同一脚本、同一台机器，41 页真实语料）：解析+切章 0.94–2.9 s，单次全流程 1.04–2.98 s。
即 200 页 ≈ 41 页的 5 倍页数，解析耗时的增长区间仍是线性的（波动见 §6.3）。

**一句话结论**：不含 LLM 的部分，200 页在 **13 秒级**完成，离 20 分钟预算差两个数量级；
真正吃掉 20 分钟预算的是 LLM 生成阶段，而它不在本文件的测量范围里（也没有可用网关可测）。

## 2. 26 章 / 199 页复测（本轮新增，修上一轮的规模失真）

上一轮 200 页是「同一份 41 页文档循环 5 次」，章标题被 `_dedupe_headings` 去重后只剩 **5 章**，
切章成本被低估。这一轮用 `scripts/build_bench_25ch.py` 把**真实语料的条款正文**重新组织到
26 个互不相同的章标题下，得到 199 页 / 2943 段 / 26 章 的长语料，重跑同一支 bench：

| 指标 | 200 页 PDF（5 章，循环拼接） | 199 页长语料（26 章） |
|---|---|---|
| 段数 | 1251 | 2943 |
| 章节数 | 5 | **26** |
| 抽取分块数 | 8 | **190** |
| 废标命中 | 40 | 209 |
| 解析 + 切章 | 12.06 s | **0.12 s** |
| 其中切章 | 0.004 s | **0.005–0.007 s** |
| 其中废标扫描 | 0.004 s | 0.006–0.008 s |
| 其中按章分块 | 0.0 s（8 块） | **0.002–0.003 s（190 块）** |
| 抽取+矩阵+导出 | 0.1–0.4 s | 0.0 s |
| 单次全流程 | 12.46 s | 0.12 s |

**读法（别把两列当同一口径比）**：

1. 两列的「解析 + 切章」**不可直接相减**。PDF 那 12 s 几乎全是 pypdf 抽文（纯 Python、单核），
   长语料是 Markdown，`MarkdownParser` 直接切页，**没有 PDF 抽文这一段**。所以 0.12 s 不是
   "200 页只要 0.12 秒"，而是"章节从 5 涨到 26、段落从 1251 涨到 2943 后，
   切章 + 分块 + 废标扫描加起来仍是毫秒级"。
2. 真正被上一轮低估的就是后三列：**26 章 / 190 块时，切章 5–7 ms、分块 2–3 ms**。
   上一轮写的「章节数放大 25 倍也在 0.3 s 量级」方向对、量级更保守；现在有实测了：
   切章不是成本项，PDF 抽文才是。
3. 因此 §1 里 PDF 口径的 12.1 s 结论不受影响：页数决定 pypdf 抽文，章节数只影响毫秒级的部分。

**仍然存在的局限**（写清楚，不糊过去）：

- 26 章语料是 **Markdown**，不是 PDF。pypdf 抽文这一段在它身上没有对应数字，
  所以"26 章 + 200 页 PDF"的端到端解析耗时**没有直接实测**，只能由"PDF 抽文按页数线性 +
  切章毫秒级"推得 13 秒级。要彻底消掉这个局限，需要能生成带中文文本的 200 页 PDF
  （当前依赖里没有 PDF 写作库，本轮不新增依赖）。
- 26 章语料的条款正文取自同一份 41 页语料并循环使用：**语域真实、章结构真实、页数真实**，
  但内容重复。它服务的是"章节规模 + 页数规模"，不服务"内容多样性"。
- 长语料跑 bench 时 `run_pipeline` 传 `relocate_spans=False`：抽取结果 JSON 来自另一份文档，
  拿它的 quote 去 26 章语料里重定位必然找不到（会被全量标 needs_review）。
  定位/回查不在这一跑的口径里，见 docs/LOCATE.md。

## 4. 命令

```bash
# A) PDF 200 页（41 页真实语料循环拼页，pypdf 本地拼接，不联网）
./.venv/Scripts/python.exe scripts/bench_200p.py --repeat 3 --out-dir out/perf

# B) 26 章 / 199 页长语料：先造语料（每条条款各自成块，解析器按 4000 字/页翻页），再跑同一支 bench
./.venv/Scripts/python.exe scripts/build_bench_25ch.py
./.venv/Scripts/python.exe scripts/bench_200p.py \
    --pdf out/perf/tender_26ch_200p.md --repeat 3 --out-dir out/perf26

# C) 41 页基线（同一脚本、同一口径）
./.venv/Scripts/python.exe scripts/bench_200p.py --pages 41 --out-dir out/perf41 --repeat 3
```

脚本做的事：

1. `out/perf/tender_200p.pdf`：`reader.pages[i % 41]`（i = 0..199）→ 200 页 / 697,958 bytes；
   源不是 PDF 时原样测（不拼页）；
2. 计时 A：`load_tender(pdf)` —— **解析 + 切章 + 废标扫描**；
3. 计时拆项：`build_sections()` / `scan_disqualifications()` / `build_chunks()` 各自单独计时
   （切块不调 LLM，用来量「章节数放大后真正会涨的那一段」）；
4. 计时 B：`run_pipeline(pdf, generate=False, save_db=False, extract_json=out/jiangsu_extract.json)`
   —— 抽取结果读盘 + 能力矩阵 + 生成计划 + 导出 docx，**0 次 LLM 调用**；
5. 明细落 `out/perf{26}/bench_200p.json`（每次运行的 parse/切章/扫描/分块/整段耗时、段落数、章节数、分块数）。

## 5. 口径声明（重要）

- **不含 LLM**：`--no-generate` 之外，抽取也走 `--extract-json`（复用已落盘的结果），
  所以 0 次模型调用、0 token。**12.5 s 是"程序侧"耗时，不是端到端交付耗时。**
- **生成阶段**才是 20 分钟预算的主要消耗方：41 页语料 ≈ 14 个抽取块 + N 个生成批次，
  每块一次或多次模型调用；200 页语料按块数线性放大。这部分本轮**没有实测数字**，
  因为没有可用网关（默认网关地址在本机不可用），也不允许在验收里伪造。
- `run_pipeline` 内部会**再解析一次**文档，因此"解析 + 其余"两段相加 = 一次完整跑；
  报告里没有把两次解析相加当成分项成本。
- **上一轮的「拼接件去重导致章节数偏少」局限：已修正**——新增 26 章 / 199 页长语料复测（§2）。
  随之而来的新局限是"26 章语料不是 PDF、不走 pypdf"，已在 §2 末尾列出，没有隐瞒。
- PDF 拼接语料仍是**同一份文档循环**（1251 段 / 200 页），段落与页数线性增长、内容重复；
  A 组数字只代表"页数规模"，不代表"内容多样性"。

### 6.3 波动来源

- 首轮磁盘/杀毒冷启动，以及机器上其它任务争抢 CPU：PDF 口径单次 12.1–25.1 s
  （同一台机器、同一份 PDF，两次跑之间可以差一倍）。**取最好成绩画像、同时报区间**，
  不拿单次最优当承诺值。
- Windows 上 pypdf 是纯 Python 单线程，页数与耗时近似线性；章节数只影响毫秒级部分（§2）。

## 7. 复现注意

- `out/perf/` 里的 docx 是 `--no-generate` 的**阶段产物**：首行带
  「本文件只有抽取与能力矩阵结果……不能作为投标文件使用」横幅，退出码 3 表示能力库是示例数据；
  它不是交付物。
- 换机器/换 Python 版本后数字会变（pypdf 是纯 Python，单核性能直接决定解析时间）；
  重新跑上面的命令即可刷新，不需要改代码。
- 26 章语料由 `scripts/build_bench_25ch.py` 生成（`out/perf/tender_26ch_200p.md`，
  2.1 MB，不入库）；生成脚本会打印页数/段落数/章节数，数字对不上就别拿它下结论。
