# BidPilot 性能实测（200 页 / 26 章）

验收尺子里有一条「200 页招标文件 ≤ 20 分钟」。这份文档记录**实测数字、命令与口径**，
避免把"含 LLM 生成"和"不含 LLM"的两种耗时混在一起比较，也避免用"章节数被去重的拼接件"
冒充规模测试。

> 口径演进：① 41 页真 PDF 循环拼成 200 页（章标题被去重成 5 章）→ ② 26 章 / 199 页 **Markdown** 语料
> （不走 pypdf）→ ③ **本轮：26 章 / 204 页真 PDF**（reportlab 生成，带中文文本层，走 pypdf 抽文）。
> 三份都留着，因为它们回答的不是同一个问题；③ 才是「200 页 + 26 章 + 真 PDF」的端到端实测。

## 1. 结论

| 口径 | 实测 | 验收尺子 | 说明 |
|---|---|---|---|
| **解析 + 切章**（`load_tender`，真 PDF **204 页 / 26 章 / 2171 段**） | **15.25 s**（3 次最好） / 15.25–19.85 s（区间） | — | pypdf 抽文 + 分页分段 + 章节切分 + 废标扫描 |
| 其中 pypdf 抽文单独计 | 11.2–18.2 s（204 页 / 316,395 字，4 次采样） | — | 纯 Python 单核；**是整条链路的成本大头** |
| 其中切章 / 废标扫描 / 分块（20 次中位） | 10.9 / 8.3 / 3.7 ms | — | 只是毫秒级，随段落数涨、不随页数涨 |
| 抽取 JSON 读取 + 能力矩阵 + 计划 + 导出（`generate=False`） | 0.1–0.2 s | — | 复用已落盘的抽取结果，**0 次 LLM 调用** |
| **单次完整跑（不含 LLM 生成，真 PDF 口径）** | bench 口径 **15.45 s** / 实际墙钟 **18.8–19.6 s** | 1200 s | 占预算 **1.29% / 1.63%** |
| 同上，26 章 / 199 页 **Markdown**（上一轮，仅作对比） | 0.12 s（不含 pypdf 抽文） | — | 口径差异见 §4 |
| 生成阶段（LLM） | **未计入（未测，需 LLM）** | — | 本轮用 `--no-generate` 跳过；见 §7 |

参考基线（同一脚本、同一台机器，41 页真实语料）：解析+切章 0.94–2.9 s，单次全流程 1.04–2.98 s。
单看页数，204 页 = 41 页的 5 倍，但**每页抽文成本不是常数**：41 页原件 834 字/页、pypdf 约 21 ms/页；
本语料 1551 字/页、74–89 ms/页（每页 3.5–4.2 倍，每字约 2 倍）。所以「页数决定量级、页内文本密度决定单价」，
见 §3 第 3 条。

**一句话结论**：真 PDF / 26 章 / 204 页，不含 LLM 的部分 **15–20 秒**完成，离 20 分钟预算差两个数量级；
真正吃掉 20 分钟预算的是 LLM 生成阶段，而它不在本文件的测量范围里（本轮也没有网关可测）。

## 3. 与 Markdown 口径对比：切章 / 分块有没有退化

同一台机器、同一支 bench、同一个条款池，唯一变量是输入格式与分页方式：

| 指标 | 26 章 / 199 页 Markdown | 26 章 / 204 页 真 PDF | 变化 |
|---|---|---|---|
| 章节数 | 26 | 26 | 0 |
| 段落数 | 2943 | 2171 | −26% |
| 正文字数 | 804,583 | 308,035 | −62%（人造页 4000 字 vs 真页 1510 字） |
| 切章（中位，20 次） | 15.5 ms | **10.9 ms** | **−30%（更快）** |
| 废标扫描（中位） | 16.6 ms | **8.3 ms** | −50%（更快） |
| 分块（中位） | 5.3 ms | **3.7 ms** | −30%（更快） |
| 分块数 | 190 | 168 | −12% |
| 块大小中位 / 最大 | 4,028 / 4,228 字 | **1,624 / 1,935 字** | 见下 |
| 解析 + 切章 | 0.12 s | **15.25 s** | ×127（全是 pypdf 抽文） |

**结论（分三条说清，不糊）**：

1. **切章没有退化**。`build_sections` 只吃 `ParsedDocument.paragraphs`，与输入格式无关；
   真 PDF 反而更快（10.9 ms vs 15.5 ms），因为段落数更少（2171 vs 2943）。
   之前记录的 0.005–0.007 s vs 0.010–0.015 s 是单次采样噪声，20 次中位才是可比的量。
   → **章节数从 5 涨到 26，切章仍是毫秒级**，这条结论在真 PDF 上成立。
2. **分块数在单位字数上变多了，但这是修正、不是退化**。Markdown 口径的「页」是 4000 字的人造页，
   `_section_chunks` 对中间页是**整页取**，于是块突破了 `max_chars=2000` 的上限（中位 4,028 字，
   是配置值的 2 倍）。真 PDF 每页 1510 字，块才真正落在 2000 字以内（中位 1,624 字）。
   换算成同一字数口径：真 PDF 每 1,833 字切 1 块，Markdown 每 4,234 字切 1 块 ——
   **同样 80 万字在真 PDF 下会切出约 430 块，是上一轮 190 块的 2.3 倍**。
   也就是说上一轮低估的不是"切章"，而是**LLM 调用数（块数）**：真 PDF 要按 2.3 倍算预算。
3. **解析的成本结构没变**：页数决定 pypdf 抽文的量级，章节数只影响毫秒级部分。
   真 PDF 上「解析+切章」15.25 s，与 5 章 / 200 页拼接件（12.06 s）同量级。
   单价差异有实测：41 页原件 834 字/页 → 21 ms/页；本语料 1551 字/页 → 74–89 ms/页
   （每字约 2 倍）。页数与文字量都能解释量级，**页内每字的抽文单价与输入 PDF 的生成方式有关**
   （本语料是 TTF 子集嵌入，抽文时要走 ToUnicode 还原 —— 这一点是推测，没有单独做对照实验），
   与章节数无关。

**仍然存在的局限**：

- 条款正文取自**同一份 41 页语料**并循环使用（188 条池子）：语域真实、章结构真实、页数真实，
  但**内容重复**。它服务「章节规模 + 页数规模 + 抽文成本」，不服务「内容多样性」。
- 条款池沿用 `build_bench_25ch.py` 的清洗，含少量真实 PDF 的**页眉/页码粘连行**
  （如"……公开招标文件第 1 页 共 41 页……"）。两份语料同源同噪声，不影响两者对比；
  它会让"页数"这个词在语义上有点滑稽（204 页的文档里写着"共 41 页"），但不影响解析/切章/分块计量。
- 跑 bench 时 `run_pipeline` 传 `relocate_spans=False`：抽取结果 JSON 来自 41 页原文档，
  拿它的 quote 去 204 页语料里重定位会大面积找不到（会被标 needs_review）。
  定位/回查不在这一跑的口径里，见 docs/LOCATE.md。
- **生成阶段（LLM）仍未测**：本轮 0 次模型调用，20 分钟预算里最大的那一项没有数字。

`bench_200p.py` 做的事：

1. 源是 PDF 且**不足** `--pages` 页时循环拼页到目标页数（A 组 204 页已够页，**原样测不拼页**，
   否则会把最后一章截掉）；源不是 PDF 时原样测；
2. 计时 A：`load_tender(pdf)` —— 解析 + 切章 + 废标扫描；
3. 计时拆项：`build_sections()` / `scan_disqualifications()` / `build_chunks()` 各自单独计时；
4. 计时 B：`run_pipeline(pdf, generate=False, save_db=False, extract_json=out/jiangsu_extract.json)`

5. 明细落 `out/perf{26,26pdf,41}/bench_200p.json`（每次运行的 parse/切章/扫描/分块/墙钟/段落/章节/分块数）。

`make_bench_pdf.py` 做的事：从 41 页真实语料取 188 条条款正文 → 按 26 章组织（每章另起一页）
→ reportlab 排版 → **用 `pypdf` 数页、用 `load_tender` 自检章节数**，不达标就自增字数重排
（最多 5 轮），章节数少于 26 直接失败退出。生成的 PDF **不入仓**（`out/` 已被 `.gitignore` 忽略，
不到 1 MB 且 30 秒可重生成），只保留命令。

## 7. 口径声明（重要）

- **不含 LLM**：`--no-generate` 之外，抽取也走 `--extract-json`（复用已落盘的结果），
  所以 0 次模型调用、0 token。**15–20 s 是"程序侧"耗时，不是端到端交付耗时。**
- **生成阶段未测（需 LLM）**：41 页语料约 14 个抽取块 + N 个生成批次，每块一次或多次模型调用；
  §3 已指出真 PDF 口径下块数要按 2.3 倍算。这部分本轮没有实测数字，也不允许在验收里伪造。
- `run_pipeline` 内部会**再解析一次**文档，所以它在真 PDF 上的墙钟（18.8–19.6 s）约等于两次抽文；
  bench 的「单次全流程」口径 = `load_tender` + parse 之后的其余部分（15.45 s）。
  两个数都写出来了，别混用。
- 「26 章 + 200 页」的输入格式限定**已消掉**：§2 是 204 页真 PDF、26 章、走 pypdf 抽文。
  剩下的限定只有"内容重复（同一份 41 页语料的条款池）"和"生成阶段未测"，见 §3 末尾。
- §4 的 PDF 拼接语料仍是**同一份文档循环**（1251 段 / 200 页），只代表"页数规模"，不代表"内容多样性"。

### 8.4 波动来源

- 首轮磁盘/杀毒冷启动，以及机器上其它任务争抢 CPU：PDF 口径单次 12.1–25.1 s
  （同一台机器、同一份 PDF，两次跑之间可以差一倍）。真 PDF 204 页上同样的波动是 15.25–19.85 s。
  **取最好成绩画像、同时报区间**，不拿单次最优当承诺值。
- Windows 上 pypdf 是纯 Python 单线程，页数决定抽文的量级；章节数只影响毫秒级部分（§3）。

### 8.5 切章/扫描/分块的 20 次中位怎么复现

`bench_200p.py` 每次运行只采样一次，单次 5 ms 级的数会被噪声吃掉（同一份语料能读出 5 ms 也能读出 15 ms）。
§2/§3 的中位数用下面这段跑出来（对两份语料各取 20 次中位）：

```python
import statistics, sys, time
sys.path.insert(0, "src")
from bidpilot.extract import build_chunks
from bidpilot.sections import build_sections, load_tender, scan_disqualifications

def med(fn, n=20):
    xs = []
    for _ in range(n):
        t = time.perf_counter(); r = fn(); xs.append((time.perf_counter() - t) * 1000)
    return statistics.median(xs), r

for label, path in [("真PDF 204p/26ch", "out/perf/tender_26ch_200p.pdf"),
                    ("MD  199p/26ch", "out/perf/tender_26ch_200p.md")]:
    doc = load_tender(path)
    secs = build_sections(doc.parsed)
    print(label, "sections", med(lambda: build_sections(doc.parsed))[0],
          "disq", med(lambda: scan_disqualifications(doc.parsed, secs))[0],
          "chunks", med(lambda: build_chunks(doc))[0])
```

## 9. 复现注意

- `out/perf*/` 里的 docx 是 `--no-generate` 的**阶段产物**：首行带
  「本文件只有抽取与能力矩阵结果……不能作为投标文件使用」横幅，退出码 3 表示能力库是示例数据；

  重新跑上面的命令即可刷新，不需要改代码。
- 26 章 Markdown 语料由 `scripts/build_bench_25ch.py` 生成（`out/perf/tender_26ch_200p.md`，
  2.1 MB，不入库）；26 章真 PDF 由 `scripts/make_bench_pdf.py` 生成
  （`out/perf/tender_26ch_200p.pdf`，959,272 bytes / 204 页，同样不入库）。
  两个脚本都会打印页数/段落数/章节数，**数字对不上就别拿它下结论**。
